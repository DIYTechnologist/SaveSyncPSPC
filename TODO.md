## RE Engine family (RE3/RE4/RE7/Village/Requiem):

Real PS5 saves captured for all five (Garlic, uid `1ea2f4da`, title IDs `PPSA03952`/`PPSA07411`/`PPSA04400`/`PPSA01556`/`PPSA31246`). All use `DSSS` magic/version 2 and all five have valid murmur3 checksums, but **which cipher a save uses varies by title *and* platform** - a title's PS5 save and its Steam save frequently don't match. Findings below were each confirmed by decrypting/parsing the real files, not inferred. See `docs/dev.md` and `docs/dev-res2.md` for the full reference.

**RSZ reader/writer bug found and fixed (2026-08-09), affects every title on this engine.** A sized value's position is *not* computed by aligning up to its declared size, as this package assumed: RE Engine applies the bit mask `(pos + size - 1) &^ (size - 1)`, which only coincides with true alignment when `size` is a power of two. Every size in RE2/RE3/RE4/RE7/Village saves is 1/2/4/8/16, so the difference never surfaced - but Resident Evil Requiem carries 24-byte struct values (a 3-double position), where true 24-alignment lands 8 bytes short of where the mask puts it, desynchronising the reader on the very first one. Fixed in `rszCursor.alignSized` (`rsz.go`) and mirrored exactly in `rszWriter.alignSized` (`rszwrite.go`) - reader and writer must agree or a converted save desyncs when the game reads it. Confirmed against a real Requiem save: the mask predicts all 57 such values' positions exactly, the whole body then parses to completion, and all four real Requiem PC saves now round-trip **byte-identically**. Regression-tested (`TestSizedValueUsesBitMaskNotTrueAlignment`) and re-verified against every real RE2/RE3/RE4/RE7/Village save available - all still parse with unchanged round-trip results. Incidentally also fixes a latent divide-by-zero panic on a malformed save declaring `size = 0`, which the old true-alignment path hit directly (`TestAlignSizedRejectsZeroSizeWithoutPanicking`).

**Key discovery method that worked** (reusable for the remaining titles): the encrypted `DSSSDSSS` check block is a known-plaintext oracle, so *any* candidate key can be tested instantly and unambiguously. Sweeping every printable-ASCII run in the whole 336MB eboot.bin against that oracle found RE4's key in ~10 seconds - far cheaper and more reliable than disassembling to find the key-schedule call site (tried first, got nowhere).

- **Requiem - wired in and fully confirmed both directions in-game (2026-08-09).** `games/requiem.json`, engine `reengine`, title `requiem`, Steam app id `3764200`, PS5 title `PPSA31246`. **The first title here where both platforms use the same cipher and the same container shape** (Mandarin, `flags=0x10`, body at `0x10`, no `HasID`/Blowfish field on either side) - they differ *only* in the account key. That makes a conversion a pure key swap with the decrypted body carried across verbatim: no re-serialization, no re-alignment, and therefore none of the alignment-padding fidelity loss the other titles have. Confirmed lossless against real saves in both directions.
  - `internal/reengine/mandarin.go` (cipher) + `cityhash.go` (CityHash64) + `requiem.go` (conversion). The scheme: SplitMix64-seeded block sizing, per-block AES-128-OFB with SplitMix64-derived key/iv, CityHash64 per-block checksums, and the same ElGamal P/Q/R group RE4's Lime cipher uses for a per-block authenticated key/iv copy (shared with `lime.go`, not duplicated). Format facts cross-referenced against `kvasszn/ree-save-editor`'s public Rust source for facts only - not a port, except CityHash64, which is faithful because a checksum must match bit-for-bit or the format rejects the save (verified against that crate's own test vectors).
  - **Two different keys, both recovered.** PC: the **raw 64-bit SteamID64, unmasked** - a first for this project, where every other title embeds the 32-bit account ID; the engine adapter reconstructs it from the bridge's normalized account ID (`steamID64Base | accountID`), so `--steam-id` still accepts either form. PS5: a **fixed hardcoded constant** (`KeyRE9PS5 = 394424879635983`), *not* account-bound at all - console saves are already bound by the OS savedata container. Both found with a known-plaintext oracle (`MandarinKeyOracle`): the first 64 bytes of every block's metadata are the constant `x0 = r^e mod p`, so XORing them against a real file recovers PRNG mask bytes with no key, making any candidate testable in ~25 PRNG steps. The PS5 constant fell out of sweeping every 8-byte window of the real `eboot.bin` against that oracle - exactly the method that found RE4's key - matching exactly one offset (`0x4fc9fb9`) out of ~550M candidates in 7 seconds.
  - The community reference's `(0, 0x61f6868699c14dfa)` seed pair is confirmed correct, including the `0` first seed that source flagged as a likely placeholder (it only feeds an RSA-wrapped trailer this package deliberately doesn't reproduce; see `mandarin.go`). **The PS5 build uses the same seeds** - the constant is present verbatim in its `eboot.bin`.
  - **No platform-identity field**, same as RE7 and Village (searched every class in a real PC and a real PS5 save for the shared enum+bool hash pair; zero matches). Slot numbering follows the usual convention (verified: 0, 1, 10, -1).
  - **Requiem has an account-identity field, found the hard way (a failed live test).** No platform enum+bool pair exists (same as RE7/Village), but the header class carries a per-account u32 - class `0x92470294`, field `0xa4d68992` - identical across all of one account's saves and different between accounts. Leaving the Steam value in place made a real PS5 silently drop the save from its menu (only "New Game" offered), the same symptom as RE3's wrong-Steam-ID bug. It cannot be derived (murmur3/CityHash/masking of every available identifier were all tested against both known values), so the converter copies it from a save the destination already owns - the PS5 template payload the bridge already fetched but this engine ignored (closing that standing TODO), or any existing PC save for the reverse direction. Verified on real data: exactly 4 bytes differ from the source body. A build-stamp field (`0x781ee97a`) sits in the same class and is deliberately left alone; it's the next suspect if a converted save still won't load (the Deck's slot 0 carries an older stamp than the PS5's build).
  - **Key and seeds are region-independent**: two different real PS5 eboot.bin builds (one USA, different size and hash) each contain the key exactly once with identical seeds, shifted by `0x30`. No per-region handling needed.
  - **PC→PS5 confirmed loading correctly in-game (2026-08-09), on two different saves.** Each put the player at the exact scene that file's in-game entry describes ("Wrenwood / Main Street, Go after victor", then "Chronic Care Center / Room 203, escape"), both distinct from the console's own save. The account-identity field was the one and only real bug.
  - **The build stamp is a red herring** - the save that loaded carries `0x1001002` while the PS5 build carries `0x1002000`. Older-build saves are accepted. `RE9VersionField` is still left alone, but it isn't a gate.
  - **Naming caveat:** unlike RE2's convention, `dataNNNSlot.bin` does *not* mean "manual save" for Requiem - its two autosaves are `data000.bin` and `data001Slot.bin`, the manual save is `data010Slot.bin`. Only the trailing slot number is reliable.
  - **Slot retargeting confirmed in-game**: with the PS5 having a container only for slot 0, a Deck slot-1 save was pushed by rewriting its embedded slot number 1→0 to match the destination container (alongside the account id), and **it loaded correctly** - a different scene from the first confirmation, so the two corroborate each other on different saves. A save can be moved between slots, not just platforms, and the trailing slot number is the only thing needing a rewrite. Deliberately still not exposed in the CLI, where the "a save must land in its own slot" rule guards every other title (untested this way).
  - **Verification lesson worth keeping:** an intermediate conclusion that "the game served its own OS backup container instead of our file" was *wrong* - it came from comparing a coarse attribute (which character) that several saves shared, and the character mapping was itself mistaken. Compare a *distinguishing detail of the save's own content* (scene/objective/timestamp) instead. The header class gives counter `0x39a2d78e`, timestamp `0x0327223f`, account id `0xa4d68992`, build `0x781ee97a`, and the body's last 4 bytes are the slot number - enough to identify exactly which save occupies a container without launching anything.
  - **PS5→PC also confirmed in-game (2026-08-09)**, tested at two strengths: first a round trip of Deck-origin content through the real CLI (`ps5-to-pc --install`), then the console's *own* save (counter 5, never through a PC), which is the real proof for the direction. Both loaded correctly on the Deck. **Requiem is now confirmed both directions.**
  - **Remaining limitation (not a bug):** nothing here can create a PS5 savedata container - only the game can - so a PC slot with no matching PS5 container must either be retargeted into an existing slot (proven) or have a container made by saving once in-game on the console.
  - **The save-select UI orders autosaves by their internal timestamp**, so its positions and "Auto 01/02" labels shuffle when a save is replaced - installing a save with a newer timestamp looks exactly like "the wrong entry got overwritten". Identify saves by scene description or decoded header, never by list position.

**Corrections to earlier assumptions in this repo's history** (recorded so they aren't re-derived): the "Autostrong custom S-box" theory for RE3/RE7/Village was **wrong** - those PS5 saves simply aren't encrypted. `blowfish_option` is **not** a fixed-position header field; when the Blowfish flag is clear it isn't present at all, and the bytes at offset 12 are body data (which is why RE3 and Village appeared to share a "magic" value there - it was just identical RSZ header content).

## The Alters (`elbsave`, new engine, not yet wired to a `games/*.json` profile):

Installed on both the Steam Deck (Steam app id `1601570`) and the PS5 (title `PPSA16033` - Garlic has no display name cached for it, identified instead by matching its container's save-name shape to the Deck's naming). Real saves pulled from both: 86 on the Deck (`.../TheAlters/Steam/Saved/SaveGames/<steamid64>/<random-id>-ACT<n>-day-<d>-v-<archiveVersion>.sav`), 1 on the PS5 (`sdimg_<random-id>v<archiveVersion>`, same random id scheme minus the act/day suffix).

**Confirmed Unreal Engine 5.2, but *not* standard GVAS.** Every real save (both platforms) starts with `/Script/SaveSystem.ElbSaveMeta` rather than the `GVAS` magic - this project's existing `internal/gvas` parser rejects it outright (`"not an Unreal GVAS save"`), and the existing `unreal` engine adapter only supports fixed, statically-known image names (Clair's pattern), not the per-run random-ID naming this game uses on both platforms. A wholly new engine was needed, not a `games/*.json` profile on the existing one.

**A public reference existed and saved most of the reverse-engineering work**: `Iteratrix/alters-save` (a Rust save editor for this exact game) documents the outer container framing precisely - facts cross-referenced the same way as this project's other community-sourced format work (`kvasszn/ree-save-editor` for RE Engine). Ported to Go as `internal/elbsave`:

- A `.sav` file is a plaintext prefix (header/`ElbSaveMeta`/load-screen metadata/GUID lists - none of it needs to be understood to convert a save, see below) followed by a stream of 128 KiB zlib chunks (tag `0x22222222_9E2A83C1`), decompressing to the actual game-content body.
- Two `i32` fields in the prefix are EOF-relative (`value = file_len - offset - 4`) and must be rewritten if the compressed payload's length changes; found *structurally* (by their relationship to the file length and a signature byte pattern), not by fixed offset, exactly matching the reference's own approach - deliberately not interpreting the rest of the header.
- Verified against both real samples: parses cleanly, and a full decode→rebuild round trip reproduces the body byte-identically and the prefix identically outside the two intentionally-rewritten size fields (the rebuilt file is a few KB smaller than the original only because Go's zlib and whatever the game itself uses picked different compression settings for the same input - confirmed harmless, since decompression is deterministic regardless of how something was compressed).

**No platform-identity or account-binding data exists anywhere** - searched both real samples (prefix and decompressed body) for anything Steam/PSN/account/platform-shaped and found nothing, and the two saves' game-content class-path universes are effectively identical (1423 vs 1419 distinct `/Game/...`/`/Script/...` paths, same names). Unlike every RE Engine title, this project has never seen a format with *zero* content that needs retargeting - if that holds up live, a conversion is a structural validation pass, not a rewrite: decode, confirm it parses, re-encode for the destination's container.

**Decode→rebuild confirmed correct in-game (2026-08-09).** A real Deck save ("Prologue, day 1" - shown in-game under that name, not the raw `ACT0-day-1` filename) was decoded, rebuilt through `internal/elbsave` with zero content changes, verified locally byte-for-byte (body identical, prefix identical outside the two intentionally-rewritten size fields), installed back over the original file (backed up first), and **loaded correctly**. This is the same-platform round-trip check this project has used before touching cross-platform conversion for other titles (RE7/Village) - it proves the chunk framing, zlib recompression, and EOF-relative size-field patching are all correct against a real save the game itself produced, not just self-consistent.

**Still needed before a real conversion:** wiring into a `games/*.json` profile, which needs the same kind of dynamic-image-name resolution mechanism `reengine`/BG3 already have but doesn't exist for `unreal`-family engines yet (the existing `unreal` adapter only handles Clair's fixed two-file pattern).

### PC→PS5 tried live: hung on load, root-caused to a major game-version gap, not a format bug (2026-08-09)

Pushed a real Deck save (ACT3, day 74 - the most recent of the 86 available, so an unambiguous test) into the PS5's existing container with **zero retargeting** - round-tripped through `elbsave` and written as-is, testing the "no platform marker exists" theory directly. Read-back confirmed byte-identical, and the container-level structure was clearly valid: **the PS5 menu correctly displayed "ACT3 Day 74"**, proving the outer format and prefix metadata work cross-platform exactly as understood. But selecting it to actually load **hung** - not a crash, but a stuck loading screen (animations still playing, framerate still changing) that didn't resolve.

**Root cause: the two installs are two major versions apart.** PS5 is on **v1.4.2.1** (PS5 package version `1.000.013`); the Deck is on **v2.1.0.2**. Every Deck save sampled (day 1 through day 74) carries the identical engine changelist (`0x8008edaa`), meaning the Deck's entire available save history already postdates whatever changes came with the v2.x line - there is no older, version-matched Deck save left to retest with unless the PS5 is updated or an older save is found from outside the current save folder. This explains the symptom precisely: the load-menu label is read from a small prefix field that doesn't depend on the body's internal structure, so it displayed correctly regardless of version; actually deserializing the full body into live game state is where a two-major-version gap would plausibly hang rather than crash cleanly, especially for content as far into the game as day 74.

**This is not a bug in the format work** - the container repackaging, chunk framing, and prefix all round-tripped and displayed correctly; it's a genuine cross-version incompatibility, the same class of problem this project already gates for other engines (RE Engine's DSSS version field, GVAS's package-version check for Clair). The PS5 save was restored from backup immediately after and confirmed byte-identical to the original.

### PS5→PC tried too: same hang, and the "just a big version gap" theory doesn't actually hold up

Tried the theoretically-safer direction - a v1.4.2.1 PS5 save (its own "Prologue" content, installed as a brand-new file on the Deck rather than overwriting any of the 86 existing saves) loading on the newer v2.1.0.2 engine, expecting backward compatibility to save it. **Same result: appeared correctly in the load list, hung on actual load.** PS5 save restored from backup immediately after (verified byte-identical read-back).

**Structural diff between the two Prologue saves shows the version gap probably isn't the real explanation.** Compared distinct `/Game/.../Script/...` class paths between the Deck's real Prologue-day-1 save (v2.1.0.2) and the PS5's own real save (v1.4.2.1): 1,537 paths in common, **zero** present only in the PS5 save, and only **4** present only in the Deck's - all cosmetic customization assets (`DA_CustomSpacesuit_Deluxe[_Gold]`, `DA_CustomTracksuit_Deluxe[_Gold]`), plausibly a deluxe-edition cosmetic pack added between the two versions. No internal save-schema version marker exists anywhere in either decompressed body (only the container-level engine-version header, already compared). So the save *data* is almost entirely identical in shape across this version gap - a strict-subset relationship, not a restructuring. That makes "two major versions apart" too glib an explanation on its own; the real cause is more likely a byte/field-level difference within a class both versions share (a property that changed meaning, width, or ordering) that a class-path-only scan can't see, or possibly the 4 missing cosmetic references tripping some initialization path - neither distinguishable without an actual property-tree parser (per `elb.rs`'s tagged-property format), which doesn't exist yet and would be a real step up in scope from the container-level work done so far.

**Paused here.** Both cross-platform attempts fail identically (correct menu display, hang on load) regardless of direction, and the root cause is genuinely unresolved - not confidently attributable to the version gap, though a version gap is present and remains the leading suspect. Next step, if resumed: either get a version-matched pair (update the PS5, or find/preserve a pre-v2.x Deck save from outside the current save folder) to isolate whether version alone explains it, or build enough of the tagged-property parser to diff the two Prologue saves' actual field values, not just their class-path universe.
