## RE Engine family (RE3/RE4/RE7/Village/Requiem):

Real PS5 saves captured for all five (Garlic, uid `1ea2f4da`, title IDs `PPSA03952`/`PPSA07411`/`PPSA04400`/`PPSA01556`/`PPSA31246`). All use `DSSS` magic/version 2 and all five have valid murmur3 checksums, but **which cipher a save uses varies by title *and* platform** - a title's PS5 save and its Steam save frequently don't match. Findings below were each confirmed by decrypting/parsing the real files, not inferred. See `docs/dev.md` and `docs/dev-res2.md` for the full reference.

**Key discovery method that worked** (reusable for the remaining titles): the encrypted `DSSSDSSS` check block is a known-plaintext oracle, so *any* candidate key can be tested instantly and unambiguously. Sweeping every printable-ASCII run in the whole 336MB eboot.bin against that oracle found RE4's key in ~10 seconds - far cheaper and more reliable than disassembling to find the key-schedule call site (tried first, got nowhere).

- **RE3 - wired in and live-tested.** `games/re3.json`, engine `reengine`, title `re3`. PC side: plain Blowfish+HasID (`flags=0x3`, body at `0x20`), the community-sourced `KeyRE3` (previously untested) decrypts all four real saves with valid checksums. PS5 side: unencrypted (`flags=0x0`, body at `0xc`, no key needed at all). Platform-identity fields found by diffing real PC/PS5 saves: class `0x4a5aa7b` (RE3-specific) carrying the *same* two field hashes RE2 uses (`0xb41fa365` enum, `0xe231b945` bool) - the field names are shared across the engine, only the enclosing settings class differs per title. `internal/reengine` now supports both the encrypted and unencrypted PS5 shapes generically (`TitleConfig`, `Decode`/`Build`'s `flags=0` path). **Both directions confirmed via a live CLI run against real Garlic** (dry run, `--game re3`): PC->PS5 produces a correct `flags=0x0` container, PS5->PC produces a correct `flags=0x3` container, both re-parse cleanly. Not yet confirmed: loading a converted save in-game.
- **RE4 (2023) - wired in, fully confirmed in-game both directions (2026-08-08).** `games/re4.json`, engine `reengine`, title `re4`. PS5 side is plain Blowfish (`KeyRE4`, found via a known-plaintext oracle sweep of the real eboot.bin - see `docs/dev-res4.md`). PC (Steam) side uses a completely different cipher, "Lime" - implemented in Go from scratch (`internal/reengine/lime.go`): ElGamal-style modexp over a fixed public prime group (`math/big`), AES-128-OFB (`crypto/aes`), SHA3-256 per-block checksums (`golang.org/x/crypto/sha3`, newly added to `go.sum`). Fully validated against two real Steam saves pulled from a Steam Deck: every block's checksum verifies, full encode/decode round trip is byte-identical, wrong Steam ID is correctly rejected, and the complete PC→PS5→PC conversion round trip produces valid, re-parseable output. Needed a new mechanism since RE4 is the first engine needing a runtime value (Steam ID) no profile can supply ahead of time: new `--steam-id` CLI flag → `bridge.Options.SteamID` → `gameapi.SaveImage.SteamID`, the same non-interface-changing pattern `--ps5-save-name` already uses. RE4's own converter (`ConvertRE4PCToPS5`/`ConvertRE4PS5ToPC` in `internal/reengine/re4.go`) is separate from RE2/RE3's shared `TitleConfig` path, since its two sides are genuinely different cipher families. **Caveat (resolved 2026-08-08)**: `RE4PlatformClass`'s field mapping (class `0x100e60`, same field hashes as RE2/RE3) was found from a single real sample per platform, unlike RE2/RE3's multi-sample confirmation - and the boolean field showed `false` on both sides in that one sample, so it wasn't certain to be platform-discriminating for RE4. Live tests both directions (PS5→PC and PC→PS5) confirmed the mapping is correct as-is (see `TestCases.md`). See `docs/dev-res4.md` for the full writeup (the key-discovery method, the exact Lime container/cipher spec, and the CLI wiring).
- **RE7 - wired in and fully confirmed both directions (2026-08-08/09).** `games/re7.json`, engine `reengine`, title `re7`, Steam app id `418370`. Found on a Steam Deck (not this PC). PC side: plain Blowfish+HasID with `KeyRE7`, body at `0x20`, confirmed against a real save. PS5 side: unencrypted, same shape as RE3, body at `0xc`, no key needed. **Structural surprise: RE7 has no platform-identity field anywhere.** Unlike RE2/RE3/RE4, exhaustively searching every class in a real PC save (~4300 classes) and a real PS5 save (~1900 classes) for the shared enum+bool field pair (`0xb41fa365`/`0xe231b945`) found zero matches on either side. `TitleConfig.PlatformClass` now accepts zero to mean "this title has no such field - skip retargeting, container-level differences alone are sufficient" (`internal/reengine/convert.go`, covered by `TestConvertSkipsRetargetingWhenPlatformClassIsZero`). PS5→PC confirmed loading correctly in-game on a real Steam Deck. **PC→PS5's first live attempt crashed on load** ("Something went wrong with the game or application"), but re-pushing the exact same byte-for-byte output on a later attempt loaded correctly - since nothing about the file changed between the two tries, the crash was environmental (jailbreak/console instability), not a save-format bug; a same-platform PS5→PS5 round trip through this project's own RSZ writer had already confirmed the writer/alignment code itself was sound before this. Both directions are now considered confirmed working in-game. See `TestCases.md` for the full investigation log.
- **Village (RE8) - wired in and fully confirmed both directions in-game (2026-08-09).** `games/village.json`, engine `reengine`, title `village`, Steam app id `1196590`. Found on the Steam Deck (not this PC), same as RE7. PC side: `KeyRE8` (previously untested) at the usual offset, confirmed against a real save. PS5 side: unencrypted, same shape as RE3/RE7, body at `0xc`, confirmed against a real save from the PS5 (title `PPSA01556`, slot 0). Both checksums valid, both directions round-trip with zero semantic diffs. **Like RE7, no platform-identity field anywhere** - the same exhaustive shared-hash-pair search (`0xb41fa365`/`0xe231b945`) found zero matches, so `TitleConfig.PlatformClass` is zero here too. PC→PS5 applied for real and confirmed loading correctly in-game on the first attempt, slot 0. PS5→PC installed onto the real Steam Deck (backing up the live file first, since the Deck's PC save directory isn't local - needed a manual `scp` step alongside `--install`) and confirmed loading correctly in-game, tested against two different real PS5 saves (one ~1MB, one a deliberately much smaller ~417KB early save). See `TestCases.md`.
- **Requiem - genuinely encrypted, still parked.** `flags=0x10` (the `flagMandarin` bit). Does not parse as plaintext at any candidate body offset, unlike the three above. Needs the Mandarin cipher implemented in Go plus Requiem's real seed pair (`kvasszn/ree-save-editor` has a Rust `crypto/mandarin.rs` as a facts reference and a seed table, but its RE9 entry's first seed is `0` and looks like a placeholder - verify against the real save before trusting it).

- **DSSS version-based portability check, not yet implemented.** Every DSSS save carries a plaintext "version" field (u32 at offset 0x04, decodable with no key - see `docs/dev-res2.md`/`docs/dev-res3.md`; every real sample seen so far is `2`). `Decode` already parses it but `Decoded` doesn't expose it (internal/reengine/dsss.go). Proposal: surface it, then add a portability check comparing the source save's version against the destination platform's current save (the `ps5Templates`/PC-template payload the bridge already pulls but RE Engine's `ConvertToPS5`/`ConvertFromPS5` currently ignore entirely - see the ignored template params in `internal/engine/reengine/reengine.go`) - allow silently when the source is the same version or newer, warn (not block, since no cross-version incompatibility has actually been observed - every sample so far is version 2) when converting from a newer save down to an older one. Same tier-2/override shape as the existing `package-version` check for GVAS (`internal/gvas`'s `AllowPackageVersionMismatch`).

**Corrections to earlier assumptions in this repo's history** (recorded so they aren't re-derived): the "Autostrong custom S-box" theory for RE3/RE7/Village was **wrong** - those PS5 saves simply aren't encrypted. `blowfish_option` is **not** a fixed-position header field; when the Blowfish flag is clear it isn't present at all, and the bytes at offset 12 are body data (which is why RE3 and Village appeared to share a "magic" value there - it was just identical RSZ header content).
